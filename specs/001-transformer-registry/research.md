# Research: HV Transformer Registry

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-11-15

Each entry records the decision, why it was taken, and the alternatives considered. Stack choices
(NestJS, PostgreSQL, Drizzle ORM) were made by the project owner; the research below covers how to
apply them in line with the constitution.

## R1 — Runtime and module system

- **Decision**: Node.js 24 LTS, TypeScript `strict`, compiled to **CommonJS** (`module`/
  `moduleResolution: nodenext`, no `"type": "module"`). Dependencies may be ESM-only only if they
  are loadable through `require(esm)` (supported natively by Node 24).
- **Rationale**: NestJS relies on `experimentalDecorators` + `emitDecoratorMetadata`. Under native
  ESM, emitted decorator metadata referencing classes from circular imports causes
  temporal-dead-zone errors at startup, a well-known NestJS pitfall; NestJS's own packages and
  tooling (CLI, testing) are built and documented around CommonJS.
- **Alternatives considered**: native ESM (rejected: fragile with Nest DI, needs workarounds such
  as `forwardRef` everywhere); TC39 standard decorators (not supported by NestJS).
- **Constitution impact**: allowed by the *Module system* rule of constitution v1.1.0 (NestJS
  applications may compile to CommonJS).

## R2 — HTTP framework setup

- **Decision**: NestJS 11.x on the default **Express** platform adapter; one feature module
  `TransformersModule`, plus `AuditModule`, `AuthModule`, `HealthModule`, `DatabaseModule`,
  `ConfigModule`.
- **Rationale**: owner's choice; Express adapter has the broadest middleware/test ecosystem
  (supertest). Fastify adapter offers no needed benefit at the expected load (10k assets).
- **Alternatives considered**: Fastify adapter (faster, but less common with Nest middleware).

## R3 — Contract-first OpenAPI and request validation

- **Decision**:
  - The OpenAPI 3.1 document is hand-written **first** in
    `specs/001-transformer-registry/contracts/openapi.yaml`; at implementation time it is copied
    to `openapi/openapi.yaml`, the single service contract loaded at runtime.
  - TypeScript types for requests/responses are **generated** from it with `openapi-typescript`
    (`src/generated/openapi.d.ts`); no hand-written DTO classes duplicating the schema.
  - Request bodies and query strings are validated by a Nest pipe using **Ajv 2020-12**
    (`ajv/dist/2020` + `ajv-formats`, `allErrors: true`) compiled from the contract's component
    schemas. Type coercion is enabled **only** for query/path parameters (always strings on the
    wire); request bodies are validated without coercion, so `"250"` for a number is rejected
    rather than converted (constitution II). Cross-field domain rules (HV > LV > tertiary voltage, year ≤ current year, status
    transitions) run in the domain layer; schema and domain errors are **merged into one 422
    response** so every invalid field is reported at once (FR-008).
  - Contract tests validate every response against the contract with the same Ajv setup.
- **Rationale**: keeps the contract the source of truth (constitution III) instead of deriving it
  from code; OpenAPI 3.1 schemas are JSON Schema 2020-12, which Ajv supports natively.
- **Alternatives considered**: `@nestjs/swagger` + `class-validator` (code-first: the contract
  would be generated after the code, violating contract-first); `nestjs-zod` (code-first as
  well); `express-openapi-validator` (validates the contract but returns schema errors separately
  from domain errors with its own error format, breaking FR-008 and RFC 9457 consistency).

## R4 — Error format

- **Decision**: a global Nest exception filter renders all errors as **RFC 9457 Problem Details**
  (`application/problem+json`) with `type`, `title`, `status`, `detail`, `instance`, plus
  extensions `errors` (array of `{ field, message }`) for validation and `requestId`. Problem type
  URIs are relative: `/problems/<slug>` (e.g. `/problems/validation-error`).
- **Status codes**: 400 malformed JSON, 401 missing/invalid token, 403 role not allowed,
  404 not found (also for removed records seen by non-admins), 409 duplicate or invalid status
  transition, 412 stale `If-Match`, 422 validation errors (`/problems/validation-error`) and
  no-op requests (`/problems/no-changes`: patch without changes, status change to the current
  status), 428 missing `If-Match`.

## R5 — Persistence model and identity

- **Decision**: PostgreSQL **18**; primary keys are **UUIDv7** generated by the database
  (`uuidv7()`, available since PostgreSQL 18), time-ordered for index locality.
  Physical values stored as `numeric` with fixed scale (MVA `numeric(8,3)`, kV `numeric(7,3)`),
  frequency/phases as `smallint` with `CHECK` constraints mirroring the contract ranges (defense
  in depth).
- **Uniqueness (FR-003)**: inputs are trimmed before storage; a **partial unique index** on
  `(lower(manufacturer), lower(serial_number)) WHERE removed_at IS NULL` enforces case-insensitive
  uniqueness among non-removed records, so a removed entry does not block re-registration.
- **Rationale**: database-enforced invariants cannot be bypassed by concurrent requests.
- **Alternatives considered**: application-level uniqueness check only (race-prone); `citext`
  extension (extra extension for a single index); app-generated UUIDv4 (no ordering benefit).

## R6 — Data access with Drizzle ORM

- **Decision**: `drizzle-orm` with the `node-postgres` (`pg`) driver; schema in TypeScript
  (`src/database/schema.ts`); migrations generated by `drizzle-kit generate` and committed under
  `drizzle/`; triggers and expression indexes that drizzle-kit cannot express are added as custom
  SQL migrations (`drizzle-kit generate --custom`). Migrations are applied by an explicit
  `npm run db:migrate` step (and by the test global setup), never implicitly at app startup.
- **Notes**: Drizzle returns `numeric` columns as strings; the repository maps them to `number`
  (values fit safely in IEEE-754 at the chosen scale).
- **Alternatives considered**: Prisma, Kysely (not chosen by owner).

## R7 — Optimistic concurrency (FR-016)

- **Decision**: each transformer has an integer `version`, returned as a strong **`ETag`**
  (`"<version>"`). All mutating requests (`PATCH`, status change, removal, restoration) require
  **`If-Match`**; missing → 428, mismatch → 412. The update statement is
  `UPDATE … WHERE id = $1 AND version = $2`, incrementing `version`.
- **Rationale**: standard HTTP semantics (RFC 9110), no locks held between read and write.
- **Alternatives considered**: `version` field in the body (non-standard); pessimistic locking.

## R8 — Audit trail (FR-020…FR-022) and no hard delete (FR-017)

- **Decision**: one append-only table `audit_entries` written **in the same transaction** as the
  change. Each entry: action (`created`, `updated`, `status_changed`, `removed`, `restored`),
  actor (subject + display name from the token), timestamp, optional reason, and `changes` as
  JSONB array of `{ field, previous, new }`. Status changes are audit entries of action
  `status_changed` (fields `status`, `statusEffectiveDate`) — no separate table.
- **Immutability**: two layers.
  1. **Privileges**: migrations run as the schema owner (`DATABASE_MIGRATION_URL`); the service
     connects as a separate role `asset_data_app` (`DATABASE_URL`) granted only
     `SELECT, INSERT, UPDATE` on `transformers` and `SELECT, INSERT` on `audit_entries` — no
     `DELETE`, no `TRUNCATE`.
  2. **Triggers** (also stop the owner by mistake): row-level `BEFORE DELETE` on `transformers`,
     row-level `BEFORE UPDATE OR DELETE` on `audit_entries`, and statement-level
     `BEFORE TRUNCATE` on both tables (row-level delete triggers do not fire on `TRUNCATE`).
- The role itself is created outside migrations (no passwords in the repository): by
  `docker/postgres/init/01-app-role.sql` locally, by the test global setup in tests, and by the
  DBA in other environments; migrations only grant privileges to it.
- **Alternatives considered**: database-level generic audit (e.g. trigger capturing row diffs —
  loses actor/reason unless passed via session variables, harder to test); separate
  `status_changes` table (duplicates audit data, YAGNI); event sourcing (excessive complexity).

## R9 — Authentication and authorization (FR-023…FR-025)

- **Decision**: OAuth 2.0 / OIDC **JWT bearer tokens** issued by the organization's identity
  provider, verified with **`jose`** against the IdP's JWKS (`AUTH_JWKS_URI`), checking `iss`,
  `aud`, `exp`, and allowed algorithms (`RS256`, `ES256`). Roles are read from a configurable
  claim (`AUTH_ROLES_CLAIM`, default `roles`), with role names `viewer`, `editor`,
  `administrator` (cumulative). A global `AuthGuard` + `@Roles()` decorator enforce access;
  health endpoints are marked `@Public()`.
- **Non-disclosure (FR-025)**: removed transformers return 404 (not 403) to non-administrators.
- **Testing**: tests generate a local key pair with `jose` and override the JWKS provider, so no
  IdP is needed.
- **Alternatives considered**: Passport (`@nestjs/passport` + `passport-jwt`) — more indirection
  for the same result; API keys (no user identity for audit).

## R10 — Pagination, filtering and ordering (FR-010…FR-012)

- **Decision**: offset pagination with `page` (≥1, default 1) and `pageSize` (1–100, default 20);
  response `{ items, page, pageSize, totalItems, totalPages }`. Ordering
  `created_at DESC, id DESC` (deterministic tiebreaker). Filters: `status` (repeatable),
  `manufacturer` (case-insensitive exact), `hvVoltageKv` / `hvVoltageKvMin` / `hvVoltageKvMax`,
  `substation`, `bay` (case-insensitive exact), `visibility` (`active` default; `removed`, `all`
  admin-only). History uses the same pagination, ordered `occurred_at ASC`.
- **Rationale**: spec requires total counts and page navigation; at 10k rows `COUNT(*)` with
  indexes is well within SC-003.
- **Alternatives considered**: cursor pagination (no total/page numbers, unnecessary at this scale).

## R11 — Domain notation validation

- **Vector group (IEC 60076-1)**: HV symbol uppercase `D|Y|YN|Z|ZN|I` (`I` = single-phase)
  followed by one or two lower-voltage windings, each lowercase `d|y|yn|z|zn|a|i`
  (`a` = auto-connected) and a clock number 0–11, e.g. `Dyn11`, `YNd1`, `YNyn0d1`, `YNa0d1`,
  `Ii0`. Input is accepted only in canonical
  case; surrounding whitespace is trimmed. Pattern in [data-model.md](./data-model.md).
- **Cooling type (IEC 60076-2)**: four letters `[OKL][NFD][AW][NF]`, optionally combined with `/`
  for up to three stages (e.g. `ONAN/ONAF`, `ONAN/ONAF/OFAF`); input upper-cased and trimmed.
  Dry-type codes (IEC 60076-11) are out of scope (liquid-immersed HV power transformers only).

## R12 — Testing strategy

- **Decision**: **Vitest** with `unplugin-swc` (SWC emits decorator metadata, which esbuild does
  not); `supertest` for HTTP; **Testcontainers** (`@testcontainers/postgresql`, image
  `postgres:18`) for integration and contract tests; `@vitest/coverage-v8` with an 80% threshold
  on `src/transformers/domain/**`, `src/transformers/transformers.service.ts` and `src/audit/**`
  (constitution gate: domain/business logic).
  - `tests/unit` — domain rules (ranges, notation, transitions, diffing), no I/O.
  - `tests/contract` — every endpoint/status code against `openapi/openapi.yaml`.
  - `tests/integration` — full HTTP → PostgreSQL flows per user story, concurrency, triggers.
- **Alternatives considered**: Jest (Nest default, slower, weaker ESM/TS story); in-memory
  database (forbidden by constitution IV).

## R13 — Observability and configuration

- **Decision**: `nestjs-pino` for structured JSON logs; request id taken from `X-Request-Id` or
  generated, echoed in the response and in problem details; authorization headers redacted.
  `@nestjs/terminus` for `GET /health/live` and `GET /health/ready` (DB ping). Configuration via
  `@nestjs/config` with a Zod schema validated at startup (fail fast).
- **Required env**: `DATABASE_URL` (role `asset_data_app`), `AUTH_ISSUER`, `AUTH_AUDIENCE`,
  `AUTH_JWKS_URI`; optional `AUTH_ROLES_CLAIM`, `PORT` (default 3000), `LOG_LEVEL` (default
  `info`). `DATABASE_MIGRATION_URL` (schema owner) is read only by `scripts/migrate.ts`, never by
  the running service.

## R14 — Tooling

- **Decision**: npm (lockfile committed); ESLint flat config with `typescript-eslint`
  (`strictTypeChecked`, `no-explicit-any` as error) + Prettier; `docker-compose.yml` with
  `postgres:18` for local development. Exact versions are pinned in `package-lock.json` at
  implementation time.
